# 4575 账号池压力与故障测试报告

测试时间：2026-08-24（Asia/Shanghai）

## 结论

- 4575 应用层在本轮测试中未发现会阻断上线试用的已知缺陷；修复后的核心高并发请求共 4316 次，成功 4316 次，另有 486 次额度冷刷新/列表重叠请求全部成功。
- 4575 的大记录渲染、继续加载和输入响应显著好于原先出现的十秒级卡顿，浏览器中 200 次受控输入的 p95 为 8ms、最大 13ms。
- 多账号按“健康且剩余额度最高”选择新会话，并对已创建会话保持账号粘性；杀死首选账号的 app-server 后，新会话自动切到另一个健康账号，后续消息仍粘在该账号。
- 当前不能声称所有外部客户端的网络都已快于 ZeroTier：在线 Windows 节点测试时仍经东京 DERP 中继。应用和服务端已通过，客户端必须建立 Tailscale 点对点直连后，才能完成端到端网络验收。

## 并发与同步冲突

- 4 个用户并发、会话同步任务同时触发：2516/2516 成功，0 个 500/502，最慢用户路径 p95 827.83ms。
- Tailscale Serve HTTPS 两个压测进程并发：1200/1200 成功，0 个网络或 HTTP 错误，全部路径最高 p95 592.56ms。
- 主后端故障恢复后再次经 Tailscale Serve HTTPS 压测：600/600 成功，最高 p95 305.91ms。
- 修复前复现过 `database is locked`；根因是 15 秒会话同步对共享 SQLite 开启写事务时，网页请求未配置等待。修复为 WAL + 5 秒 busy timeout，并让线程索引只使用短批次事务。
- 修复后自然运行没有 `database is locked`、嵌套事务、堆溢出或 500/502 日志；最终审计时 72 次自然同步全部成功。
- 测试主动对主后端执行两次 `SIGKILL`，所以当前 `NRestarts=2` 是故障注入计数，不是自然崩溃。systemd 在 5.456 秒内恢复监听；恢复后的既有会话继续落到原 `260803` 账号。
- 线程索引历史 WAL 从 397MB 安全检查点回收到 0；主数据库和索引数据未删除。

- 真实新会话选择当前额度更高的 `260803`，第二轮以及两次主后端故障恢复后的后续轮次仍固定在 `260803`。

## 网络验收状态

- 服务端：Tailscale 运行、Serve HTTPS 正常、UDP 41641 监听、`UDP: true`、公网 IPv4 可用、NAT 映射不随目标变化。
- 4575 经本机 Tailscale Serve 的完整 API 压测为 1200/1200 成功。
- 登录用户隔离通过：使用 `gyj` 的有效会话并伪造 `x-codex-web-user-id: wxr`，后端仍解析为 `gyj`；前端请求头不能越权切换用户。
- 第一台 `.10` 生产机只安装了 ZeroTier，没有 Tailscale，因此无法解析或访问 `codex-pool.tail6856d9.ts.net`；这是未加入 Tailnet，不是 4575 宕机。
- 同一台 Windows 已确认同时运行两张网：ZeroTier 节点 `c77f7345bd` 的首选底层路径正是该 Windows 的 Tailscale IPv6，备用路径也是其 Tailscale IPv4。因此当前 ZeroTier 实际是“ZeroTier 套 Tailscale”，并非独立网络基线。
- 同一时段 ZeroTier peer 报告延迟约 229ms；Tailscale 20 次热链路 p50 约 151ms、p95 约 277ms，当前 Tailscale 热链路较 ZeroTier 报告值约低 34%。但在线 Windows 仍显示 `relay "tok"`，冷建链包可超过 1 秒，不能据此宣称端到端网络已经达到最终最优。
- 需在该 Windows 上运行 `tailscale netcheck` 和 `tailscale ping codex-pool`，放行 UDP 后重新验收到 `via <ip>:<port>`；最终跨网 HTTP 对照必须在变为 direct 后再执行。
- 第三轮最终门槛复检仍为 12/12 DERP，p50 144ms、p95 2.142s；服务端同期仍为 `UDP: true`、稳定 NAT、公网 IPv4 端点已发布、UDP 41641 正常监听。至此服务端可控项已排除。
- Peer relay 需要第三台低延迟、可被客户端访问其 UDP 端口的 Tailnet 设备，并需要 policy grant；只有当前服务端与目标 Windows 两个在线节点时，无法用服务端单边配置修复“客户端到服务端本身”的中继路径。自建 DERP 也需要额外公网基础设施。
